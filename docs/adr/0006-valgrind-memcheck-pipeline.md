# ADR 0006 — Valgrind Memcheck execution, XML evidence and diagnostics

- **Status:** Accepted
- **Date:** 2026-10-18
- **Milestone:** J3

## Context

J3 turns the J2 execution foundation into a Memcheck pipeline: an allowlisted
target is executed under Valgrind in XML mode, the raw XML is preserved as
evidence, and a canonical diagnostic report is produced. J4 will expose the
pipeline through the MCP `analysis_*` tools; J3 therefore adds no MCP tool and
no CLI command.

Valgrind XML is a real, tool-defined format (`<valgrindoutput>`,
`<protocolversion>`, `<error>`, `<errorcounts>`, `<suppcounts>`,
`<error_summary>`, …). It is not interchangeable with the text output, and a
truncated document must never be interpreted as "no errors".

## Decision

### Execution and argument construction

- The Valgrind binary is discovered at startup by the existing capability
  registry, using an absolute `PATH` lookup, and is revalidated immediately
  before each run (absolute path, regular executable file). A relative or
  missing binary is a typed backend error, never a silent fallback.
- Arguments are a Go slice built by `internal/valgrind`; no shell, no
  client-supplied Valgrind flag string. Only these options are emitted:
  `--tool=memcheck`, `--xml=yes`, `--xml-file=<generated path>`,
  `--error-exitcode=42`, `--leak-check=<none|summary|full>`,
  `--show-leak-kinds=<allowlisted value>`, `--track-origins=yes` (when
  requested), `--num-callers=<1..50>`, `--suppressions=<validated profile>`
  and `--` before the target path.
- The XML path is generated by the server inside the private run directory.
  `--trace-children=yes` is rejected in J3: child XML files have to be
  collected and attributed separately, which is not implemented yet.
- The target is still resolved by `internal/policy` immediately before launch:
  configured target id, workspace-root containment, executable check and
  multiset argument allowlist. Valgrind is the executable; the target path and
  arguments follow it. The target environment is the J2 allowlist (`PATH`,
  `LANG`, `LC_ALL`, `TMPDIR` pointed at the run directory); stdin stays
  disconnected.

### Raw XML capture and quotas

- Valgrind writes `memcheck.xml` in the run directory. A watchdog polls its
  size while the job runs and cancels the process group when it exceeds
  `MaxRawXMLBytes` (default 8 MiB). After the job, the artifact store adopts
  the file: it is verified as a regular non-symlink file, truncated to the
  remaining per-run byte quota when necessary, charged against that quota and
  chmodded `0600`. Adoption truncation marks the analysis incomplete and keeps
  the truncated raw file as evidence.
- J2 streams stdout/stderr through the shared byte budget. The raw XML file is
  written directly by Valgrind, so its live bound is the watchdog, not a pipe
  quota. A target can also create untracked files in its `TMPDIR` (the run
  directory); this is the documented J2/J3 local-trust limitation until a
  system-level sandbox or cgroup quota lands.
- `result.json` remains the job manifest; `analysis.json` is the normalized
  report; `memcheck.xml` is the raw evidence. The report records artifact
  names, sizes and SHA-256 digests.

### Streaming parser

- `internal/valgrind` uses `encoding/xml` token-by-token. It never decodes a
  whole document and never uses recursive `Decoder.Skip` on untrusted
  nesting. A bounded element stack enforces `MaxDepth` (default 64).
- Limits: total bytes, diagnostics (default 10 000), frames per stack (default
  128), frames per document (default 65 536), context stacks per diagnostic
  (default 8), string bytes (default 4096) and suppression entries (default
  512). Reaching a limit sets
  `truncated` and is treated as an incomplete analysis; it is never silently
  ignored.
- A clean EOF is accepted only after `</valgrindoutput>`. Missing end tag,
  syntax error, unexpected root, depth overflow or a decoder error yields a
  partial `XMLResult` plus a typed parse error; the caller keeps the diagnostics
  parsed so far and marks `analysis_complete=false`.
- Unknown elements and attributes are ignored so newer Valgrind releases remain
  readable, but the raw document is always kept as the source of truth.
- `protocoltool`/`tool` must be `memcheck`; a different tool is a tool error.
  Missing fields are reported, not invented.
- Multiple `<stack>` elements are preserved as the primary stack plus labelled
  context stacks; `<origin>` keeps its own stack (track-origins).
  `<errorcounts>` attaches occurrence counts to diagnostics by `<unique>`;
  `<suppcounts>` becomes the suppression list.

### Canonical diagnostics

- `internal/diagnostic` owns the `schema_version = 1` report and diagnostic
  model. It preserves `tool_reported` confidence for observed data; no field is
  inferred by the server except documented severity policy and fingerprints.
- Stack frames keep function, object, raw-derived path and line. Workspace-root
  paths are normalized to slash-separated relative paths; other paths stay
  absolute. Valgrind runtime frames (`vgpreload_*`, `/usr/lib*/valgrind`,
  `/usr/src/valgrind*`) are flagged and excluded from the primary location and
  from fingerprints. A missing file/line is not invented.
- Fingerprint v1 is SHA-256 over `origin + kind + selected non-runtime frames`
  (`function`, normalized path, line). Addresses, PIDs, TIDs, run ids and
  absolute temporary paths do not participate. Fingerprints are versioned and
  are not a proof of identity.
- Severity is a documented policy, not tool truth: Memcheck memory errors and
  definitely/indirectly lost leaks are `error`; possibly lost is `warning`;
  still reachable is `info`. Unknown kinds are `warning` and keep their raw
  kind. Summary `total` counts tool-reported occurrences, while
  `diagnostic_records` counts distinct records; each diagnostic exposes
  `occurrences`.

### Exit codes and result classification

- `--error-exitcode=42` is a marker, not proof. XML is authoritative: the job's
  exit code is preserved as the instrumented outcome, and a program that
  legitimately exits `42` with a complete, error-free XML is not reported as
  finding errors.
- `errors_found` requires a complete XML with `error_summary.errors > 0`.
  `no_errors_observed` requires a complete XML with zero errors (suppressed
  errors are reported separately and produce a warning). Missing, truncated or
  unparsable XML, capture limits, timeouts and cancellations produce
  `incomplete` or `tool_error`, never `no_errors_observed`.
- A target terminated by a signal is reported with its signal. It does not by
  itself make the analysis incomplete when Valgrind finished the XML document.

### Suppressions

- Configuration may define `valgrind.suppressions`: profile id → suppression
  file. Profile ids follow the target-id pattern; files must be absolute,
  inside a workspace root and at most 1 MiB. At invocation the path is resolved
  with `EvalSymlinks`, revalidated inside the roots and opened without following
  a final symlink.
- Suppressed errors never appear as diagnostics and are never called resolved.
  They are reported as tool-reported suppression counts; `no_errors_observed`
  with suppressed entries carries an explicit warning that suppression is not
  evidence of absence.

### Capability probe

- The Valgrind probe resolves the binary, runs `--version`, then
  `--tool=memcheck --help` with a short timeout and a minimal environment. It
  requires the Memcheck tool name and the `--xml=yes` / `--error-exitcode`
  options in the help text. It never runs a user program and never uses sudo.
- The probe reports `available` only when both checks pass. `Service.Start`
  revalidates the binary and returns a typed `BackendError` when it is missing
  or not executable. If the binary disappears between validation and `exec`,
  the asynchronous job records a `tool_error` result with no usable evidence;
  J4 maps that outcome to its named backend error. Neither path can produce a
  false "no errors".

## Consequences

- J3 exposes no new MCP tool; `internal/valgrind.Service` is the internal
  contract J4 will wrap with `analysis_start/status/report`.
- Truncated XML, skipped limits, missing evidence and contradictory exit codes
  all have explicit incomplete/tool-error paths covered by tests.
- Live disk usage of the raw XML is bounded by a watchdog and post-run
  truncation, not by a kernel quota. Files created by the target in `TMPDIR`
  remain untracked. Both are documented limitations, not hidden guarantees.
- `trace_children`, Helgrind/DRD and multi-process XML aggregation remain
  future work (J9).
